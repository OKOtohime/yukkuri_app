## 1. 引言

### 1.1 目的

本计划定义 yukkuri_app 的测试范围、方法、环境、资源、进度、风险和交付物，用于验证 `docs/requirements.md` 中的全部功能需求（FR）和质量需求（QR）。

### 1.2 背景与约束

- 测试方**不是仓库所有者**：不修改产品代码，只记录缺陷。
- 测试代码放在独立的 `qa/` 目录中，与上游的 `tests/` 分开。上游 `tests/` 只作为回归基线来执行。
- **判定口径**：遵循需求文档 1.6 节，只用外部可观察的行为判定。附录 A 中的实现约定只作为白盒测试的线索；与实现约定不一致时记观察项（OBS），不记缺陷。
- 依赖的专有组件 AquesTalk1 使用**评价版**。评价版会把 na/ma 行等音节替换为 "nu"，这是预期现象，不判为缺陷。

| 产品说明 | `README.md` |

## 3. 测试范围

### 3.1 要测试的特性

`docs/requirements.md` 第 4 节全部 FR 和第 5 节全部 QR。两个平台（Linux、Windows）同等覆盖。仅适用于单一平台的需求，只在对应平台测试。

### 3.2 不测试的特性

| 不测项 | 理由 |
| --- | --- |
| ASR 模型、VAD 模型本身的算法质量 | 第三方模型。但集成后的识别质量通过 QR-FUNC-01~05 评测 |
| AquesTalk 引擎内部的合成音质 | 专有黑盒，只测接口行为和错误处理 |

| 纯 PulseAudio 系统（非 PipeWire） | QR-COMP-04 中为可选项，有条件时补测 |

| 设计决策和技术选型是否合理（库选型、架构、算法选择） | 没有 ADR 或设计文档，测试方不评价开发者意图（需求文档 1.6 节） |

### 4.4 音频注入与采集方案（系统测试的关键基础设施）

#### 4.4.1 Linux（R1/R2/R3）

```
测试 wav ──pw-play──▶ yk_test_in (null-sink) ──monitor──▶ yk_test_mic (remap-source)
                                                              │ 应用 --device 指向它
                                                              ▼
                                                        yukkuri 应用
                                                              │ pw-play --target yukkuri_sink
                                                              ▼
                       pw-record ◀── yukkuri_source（被测的虚拟麦输出）
外放监测：yk_fake_speaker (null-sink) 设为默认 sink，用 pw-record 录它的 monitor
```

- 输入注入和输出采集都用 PipeWire 节点完成，不依赖物理声卡，因此可以在 CI 类环境和虚拟机中运行。
- 外放监测：把一个假的物理扬声器（null-sink）设为系统默认输出，录下它的 monitor。QR-SEC-01 要求这里的合成音能量为 0。

#### 4.4.2 Windows（W1）

W1 原有的 VB-CABLE 被应用占作输出，因此**另装一条虚拟线路（VB-CABLE A+B 或 Hi-Fi Cable）作为注入线路**（v0.2 已确认）：

```
测试 wav ──WASAPI──▶ CABLE-A Input ──▶ CABLE-A Output ──(--device)──▶ yukkuri 应用
                                                                         │
                       录制 ◀── CABLE Output ◀── CABLE Input ◀───────────┘
```

如果注入线路安装失败，兜底方案是在测试工具里用文件流替换 `sounddevice.InputStream`。这个方案覆盖不到设备层，用它得到的结果在报告中要注明。

外放监测：把 VM 的默认播放设备录下来（WASAPI loopback），检查其中是否有合成音。

#### 4.4.3 延迟测量

- 注入时记录每句最后一个语音样本的时间戳（以工具的单调时钟为准），采集端检测合成音第一个非静音样本的时间戳，两者之差即为延迟。
- **标定**：先让注入直接通到采集（不经过应用），测出测量链路自身的延迟，结果中扣除。要求测量误差不超过 ±20ms。
- 同时记录应用打印的 t_asr、t_g2p、t_tts，用来把延迟拆分到各阶段。

## 6. 通过与失败准则

### 6.1 单个测试用例

- **功能用例**：实际结果与需求或基线裁定一致即为通过。
- **质量用例**：度量值满足需求第 5 节中的阈值即为通过。诊断指标（QR-PERF-02/03）只记录，不判定。阈值的校准按需求第 5.0 节的规则执行。
- **概率性用例**（识别、延迟）：按样本统计量（P50、P95、均值）判定，不按单次结果判定。报告中要写明样本量。

### 6.2 缺陷严重程度

| 级别 | 定义 | 示例 |
| --- | --- | --- |
| S1 致命 | 崩溃、数据泄露、隐私破坏，没有绕过办法 | 合成音外放到物理扬声器；导入压缩包时写到目标目录之外 |
| S2 严重 | M 级需求不满足，或主流程不可用 | 声线热切换失效；端到端延迟 P95 超过阈值 50% 以上 |
| S3 一般 | S 级需求不满足，或有绕过办法 | GUI 参数范围与基线不一致；错误提示缺少修复命令 |
| S4 轻微 | 文档、文案、C 级需求 | README 声线描述错误 |

**观察项（OBS）**：实现与附录 A 实现约定或代码自述不一致，但没有造成可观察的需求偏差。观察项不分级，汇总在测试报告里，不计入准出统计。

只出现在 Windows 上、且与 README 实验性声明相关的缺陷，严重程度可以下调一级，但 **S1 隐私类缺陷不下调**。

### 6.3 准入准则

- 需求文档 v0.2 已通过评审（已满足）；
- WP-01 完成：R1 上 9 种声线和全部模型就绪，`--check` 全绿，并记录了上游单测的基线结果；
- 注入和采集工具标定完成，测量误差不超过 ±20ms（准入 L3 和性能测试的前提）。

### 6.4 准出准则

- 所有 M 级 FR 和 QR 在适用的平台上都已执行，执行率 100%；S 级执行率 ≥ 90%；
- 没有未关闭的 S1；未关闭的 S2 都附有风险说明，并在测试总结报告中明确列出；
- QR-FUNC 评测报告、性能报告、可靠性报告都已产出；
- 需求追溯矩阵（第 10 节和用例级 RTM）中，每个 M 级需求至少有 1 个已执行的用例。

### 6.5 暂停与恢复准则

| 暂停条件 | 恢复条件 |
| --- | --- |
| 环境不可用（声线库或模型缺失、VM 无法连接） | 环境恢复，并重新执行冒烟测试 |
| 冒烟测试失败（应用无法启动，或没有任何输出） | 定位到原因（环境问题修复；产品问题记缺陷后跳过受阻的用例） |
| 上游有新提交 | 评估影响后，更新测试项版本并执行回归 |
| 测量工具的误差超过 ±20ms | 重新标定 |

## 11. 风险与应对

| ID | 风险 | 可能性 | 影响 | 应对 |
| --- | --- | --- | --- | --- |
| RK-01 | W1 上注入线路（第二条虚拟线路）安装失败或驱动不稳定 | 低 | 高（阻塞 Windows 上的 L3 和性能测试） | 兜底：用文件流替换输入流，报告中注明覆盖不到设备层 |
| RK-02 | W1 是虚拟机，只有 2 vCPU，延迟受虚拟化干扰 | 高 | 中 | 用 R2（2 核）对照，区分算力因素和平台因素；报告中注明 |
| RK-03 | AquesTalk 评价版的发音限制影响听感判断 | 确定 | 低 | 听感类判断排除 na/ma 行的音节；功能判定以返回码和音频非空为准 |
| RK-04 | 语料下载量大，许可有限制 | 中 | 中 | 只抽样 ≥ 500 句；语料不入库；尽早启动 WP-07 |
| RK-05 | 合成的混说语料使结果偏乐观 | 中 | 中 | 只用真人子集判定（需求 5.1.1 节） |
| RK-06 | 难以对 GUI（CustomTkinter）做自动化 | 中 | 中 | 逻辑层用程序驱动控件回调，配合 Xvfb；视觉和交互用手工检查单 |
| RK-07 | 阈值是估计值，可能不合理 | 中 | 中 | 按需求 5.0 节的规则先测量后校准，并记录变更 |
| RK-08 | 系统测试修改 PipeWire 拓扑，影响宿主机的日常音频 | 中 | 低 | 测试工具在 teardown 中卸载自己创建的全部模块；测试前后对比 `pactl list short modules`；L3 尽量在 R3 上先演练 |
| RK-09 | 上游在测试期间更新代码 | 低 | 中 | 固定测试版本 `b993c40`；新版本走 6.5 节的流程 |
| RK-10 | 测试运行时的声音外放到测试者的扬声器 | 中 | 低 | 外放监测时用假扬声器（null-sink）作为默认输出 |
