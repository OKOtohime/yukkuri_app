## 1. 引言

### 1.1 目的

仓库只提供功能描述（README），没有成文的需求和质量指标。本文档由测试方在**非仓库所有者**的立场上，从 README、源码和产品定位反向整理出功能需求，并对质量需求做出**可度量的估计**，作为测试的判定基线（test oracle）。

### 1.2 需求来源标记

| 标记 | 含义 | 可信度 |
| --- | --- | --- |
| **R** | README 明确声明 | 高：对用户的承诺 |
| **C** | 源码实现推导（代码行为、注释、提示信息） | 中：实现即意图，但可能本身有误 |
| **E** | 测试方根据产品定位估计（主要是质量指标） | 需评审确认 |

当 R 和 C 冲突时，按第 3 节的基线裁定处理。

### 1.3 验证方式标记

**T** 测试（Test）· **A** 分析（Analysis）· **I** 检查（Inspection）· **D** 演示（Demonstration）

### 1.4 优先级

**M** 必须（Must）· **S** 应该（Should）· **C** 可以（Could）。M 级需求不满足即构成阻断发布级缺陷。

### 1.5 术语

| 术语 | 说明 |
| --- | --- |
| 切片（segment） | VAD 断句后送入 ASR 的一段语音 |
| 音标串（koe） | AquesTalk 可接受的假名音记号串 |
| 虚拟麦 | Linux：`yukkuri_sink` 的 monitor 经 remap 得到的 `yukkuri_source`（Yukkuri_Virtual_Mic）；Windows：VB-CABLE 的 `CABLE Output` |
| 端到端延迟 | 见 QR-PERF-01 定义 |
| CER / WER | 字错误率 / 词错误率 |
| R1 / R2 / W1 | 参考测量环境，见第 6 节 |

### 1.6 需求判定原则

1. **只用外部可观察的行为判定**：需求描述的是用户通过 CLI、GUI、日志、虚拟麦输出和文件系统能看到的结果，不描述"怎么实现"。
2. **实现细节不当作需求**：从源码观察到的算法、参数取值和内部顺序列在附录 A，只作为白盒测试的线索。它们和代码自身意图不一致时，记为观察项，不记缺陷（见附录 A.1）。
3. **设计决策和技术选型不在评估范围内**：项目没有 ADR 或设计文档，测试方不评价"为什么这样设计"、"为什么选这个库"。可维护性仍然评估，但只看可度量的结果（见 5.7 节），不评价设计取舍本身。
4. **来源为 C 的需求**：只保留那些对用户可观察、且明显体现保护用户意图的行为，例如隐私不外放、退出后清理、错误提示。

## 2. 产品概述

### 2.1 处理链路

```
物理麦克风 → MicrophoneStream(自适应采样/下混/增益/重采样至16k)
          → SileroVAD(停顿断句/最长截断) → ASR(SenseVoice|Vosk)
          → PolyglotG2P(中/英/日/数字 → 假名) → AquesTalk1(声线/语速 → 8kHz WAV)
          → AudioPlayer
               ├─ Linux:   输出增益 → pw-play/paplay --target yukkuri_sink → yukkuri_source
               └─ Windows: 输出增益 → 重采样+升混 → WASAPI → CABLE Input → CABLE Output
```

### 2.2 用户接口

1. **CLI**：`yukkuri` / `run.sh` / `python -m yukkuri.cli`
2. **GUI**：`yukkuri-gui` / `run.sh --gui` / `run.bat`（CustomTkinter）
3. **模型配置工具**：`setup_models.py`（跨平台）/ `setup_models.sh`（Linux）/ GUI 模型管理对话框
4. **辅助脚本**：`setup_virtual_mic.sh`（写入常驻 PipeWire 配置）

### 2.3 用户角色

| 角色 | 典型场景 |
| --- | --- |
| 主播/开黑玩家 | 在 Discord、OBS、腾讯会议中以油库里音色说话 |
| 静默用户 | 不开口，用 GUI 文字播报推流 |
| 授权用户 | 持有 AquesTalk DevKey/UsrKey，需要解除评价版限制 |

### 2.4 约束与假设

- AquesTalk 动态库为专有软件，不随仓库分发，测试方需自行从 AQUEST 官网获取评价版。评价版会把 na/ma 行等音节替换为 "nu"，**属于预期现象，不判为缺陷**。
- ASR 模型为第三方（SenseVoice-Small int8 和 Vosk small），模型本身的识别能力不作为缺陷判定对象。但**集成后的识别质量**（含 VAD 切分、重采样带来的损失）纳入质量需求（QR-FUNC-01~03）。
- README 声明 Windows 为实验性支持。按测试范围约定，两平台**同等覆盖测试**；Windows 上未达标的项按缺陷记录，严重程度可参考该声明酌情下调。

## 5. 质量需求

> 以 ISO/IEC 25010:2023 为框架。标为"诊断指标"的项不单独判定通过或失败，只用于分析端到端指标。所有阈值均为 **E（测试方估计）**，依据见"估计依据"列。测量环境见第 6 节。

### 5.0 阈值校准规则

阈值是测试方在没有仓库所有者输入的情况下做的估计。为避免"凭感觉定门限"，约定以下规则：

1. 首轮执行时**先测量后判定**：如果实测值与估计阈值相差超过 2 倍，在测试报告中提出阈值修订建议，评审通过后才改阈值，不能在执行中私自放宽。
2. 标为 **M** 的 QR 不允许因为实测不达标而放宽，只能记录缺陷。
3. 所有修订都记录在第 8 节的变更记录里。

#### 5.1.1 ASR 评测约定

- **文本归一化**：SenseVoice 开启了 ITN（`use_itn=True`），会输出阿拉伯数字和标点，而 AISHELL 的参考文本是汉字数字、没有标点。不做归一化，CER 会被系统性高估。打分前，假设和参考文本统一做以下处理：去掉标点和情感标签；中文数字统一（阿拉伯数字转汉字）；英文统一小写并展开缩写；日文统一全角和半角。归一化脚本随评测报告一起交付，以便复现。
- **混说语料的合成部分**：
  - 至少用 2 种 TTS 引擎、合计 4 个以上音色，并叠加真实房间混响或噪声；
  - 避免只用与 SenseVoice 同源的 TTS（例如 FunAudioLLM 的 CosyVoice），因为训练数据可能重叠，结果会偏乐观；
  - 每条语料标注来源（真人或合成）、引擎和音色；
  - 文本脚本由测试方编写，真人和合成共用同一批脚本的不同条目。
- **数据集许可**：AISHELL-1（Apache-2.0）、LibriSpeech（CC BY 4.0）、Common Voice（CC0）、MUSAN（各子集 CC 系列许可）。语料只在本地使用，不提交到仓库。

所有性能数据都要注明环境 ID、引擎、声线和参数配置。性能门限只在对应的环境下判定。W1 是虚拟机，音频时钟和调度抖动可能使延迟偏高。W1 不达标时，先用 R2 的同算力数据排除算力因素，再判定是平台问题还是虚拟化造成的。
